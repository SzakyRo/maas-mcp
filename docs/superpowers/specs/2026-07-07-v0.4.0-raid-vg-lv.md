# v0.4.0 — RAID + Volume Groups + Logical Volumes

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Close the third storage tier — RAID arrays, volume groups, and the logical volumes that nest inside VGs — bringing the curated surface to 43 verbs and giving `storage_summary` real counts for all three tiers.

**Architecture:** Add 12 new curated verbs (5 RAID, 5 VG, 2 LV) using the same class + `Annotated[MaasClient, SkipJsonSchema()]` + `_validate_ids` + `confirm` gate pattern that v0.3.0 and v0.3.1 established. Extend `_storage_paths.py` with six new path helpers. Evolve `storage_summary` to a sequential-Stage-1 / fat-Stage-2 fetch shape that includes raids, volume groups, and logical-volume counts.

**Tech Stack:** Python 3.12+, FastMCP, Pydantic v2, respx (test mocking), pytest-asyncio, ruff, mypy --strict. Same stack as v0.3.0/v0.3.1; no new dependencies.

## Background

v0.3.0 (`cad89b7`) shipped the first two storage tiers — block devices and partitions — and v0.3.1 (`c75589b`) polished their validation. The third tier (RAID + VG + LV) was explicitly deferred in `storage_summary.description`:

> "raid_devices=0 and volume_groups=0 placeholders (RAID/VG counts land in v0.4.0)"

v0.4.0 closes that gap. The MAAS API for these resources is well-documented in `maasapi.md` lines 8753–8910 (RAIDs), 12191–12426 (volume groups), and 12311–12359 (logical-volume actions).

## Global Constraints

These apply to every change in v0.4.0 unless explicitly overridden. Re-read before each task's review.

- **No new dependencies.** Same `pyproject.toml` as v0.3.1.
- **No README or docstring rewrites beyond the verb inventory list.** v0.4.0 is the next planned release.
- **`_validate_ids` is the only validator.** Every new verb validates its path IDs through `_validate_ids(system_id, ...)` — never inline `if not system_id` / `if id <= 0` blocks. v0.3.1 closed this duplication finding (M1/M5).
- **`confirm: bool = False` on every destructive verb.** Path validation runs BEFORE the confirm check, preserving the M6 invariant. Destructive verbs are: `create_raid`, `update_raid`, `delete_raid`, `create_volume_group`, `update_volume_group`, `delete_volume_group`, `create_logical_volume`, `delete_logical_volume`.
- **`Annotated[MaasClient, SkipJsonSchema()]` first-param pattern** on every verb's `run` signature. No FastMCP JSON-schema regressions.
- **MCPUpstreamError body-strip security fix (`5ad4a1a`) preserved.** Tests asserting on upstream errors continue to assert on the status code only (`"409" in str(exc_info.value)`), never on body text.
- **Schema-drift raise on non-dict upstream** (M2). The two `get_*` verbs (`get_raid`, `get_volume_group`) and the two create verbs (`create_raid`, `create_volume_group`) raise `ValueError("MAAS returned non-dict for ...; schema drift?")` instead of silently returning `{}`. This extends the v0.3.1 M2 fix to the new verbs.
- **`MaasClient.post()` signature is `async def post(self, path, *, json=None) -> Any`.** The kwarg name is `json=`, NOT `data=`. Internally (`5ad4a1a`) the client converts the dict to multipart/form-data so MAAS accepts it.
- **MAAS authority.** Every endpoint shape, body field name, and response contract comes from `maasapi.md` at the project root. When this spec says "POST X with body Y", that must be exactly what `maasapi.md` documents for that endpoint.
- **No `Annotated[..., SkipJsonSchema()]` for body fields that are already Pydantic primitives.** Only the `client` parameter needs the annotation to suppress its schema.
- **Local-only, no PyPI publish, no push.** Matches v0.3.0 (`cad89b7`) and v0.3.1 (`c75589b`) precedent.
- **`v0.4.0` tag at post-review HEAD.** No push.

## Decisions

1. **12 new verbs, three concentric rings.** RAID outer (5 verbs), VG middle (5 verbs), LV inner (2 verbs). All flat kwargs on the create paths. Internal mapping to MAAS's `add_*`/`remove_*` fields happens inside each verb body — agents never see MAAS's asymmetric create-vs-update field naming.

2. **`create_logical_volume` and `delete_logical_volume` are write-only verbs.** MAAS exposes only `op-create_logical_volume` and `op-delete_logical_volume` (maasapi.md:12311, :12357) — no list/get for individual LVs. Agents verify LV state by re-fetching the parent VG via `get_volume_group`. This is documented in the verb descriptions.

3. **`storage_summary` field name for LV count is `logical_volumes`** (matches MAAS's docs terminology at maasapi.md:12311). Sums across all VGs in a single pass after Stage 2.

4. **LV extraction from VG responses is best-effort.** `maasapi.md` does not document the exact response field name for the LVs embedded in a VG read. `storage_summary` tries `vg["logical_volumes"]`, `vg["volumes"]`, then falls back to `0`. The agent always sees correct RAID/VG counts even if the LV-extraction guess is wrong.

5. **`create_raid` requires `level ∈ {0, 1, 5, 6, 10}`.** MAAS does not document allowed levels in `maasapi.md:8910` for the create body, but the standard mdadm set is 0/1/5/6/10. The verb validates this and raises `ValueError` with the allowed list. (This is a soft validation — MAAS itself enforces its own rules via 4xx; we surface the most common misuse early.)

6. **`create_raid` and `create_volume_group` require at least one member.** MAAS's docs note: "at least one valid block device or partition is required" (maasapi.md:12428 for VGs; same rule applies to RAIDs by definition). We surface this as a `ValueError` before the confirm check.

7. **`storage_summary` evolution uses sequential Stage 1 / fat Stage 2** (option B from brainstorming). Stage 1 fetches `list_block_devices` (must come first to size the partition fan-out). Stage 2 runs the per-device partition fan-out in parallel with `list_raids` and `list_volume_groups`. Total round-trips = `1 + N_devices + 2` (was `1 + N_devices` in v0.3.1).

8. **Path helpers colocated with `_storage_paths.py`.** Six new functions, all one-liner f-strings. No new module.

9. **No per-resource summary cross-check.** `storage_summary` reports each tier's count independently. An agent that wants the relationship "this VG contains these LVs" calls `get_volume_group` directly.

## Scope: Out of v0.4.0

- **MAAS storage layouts.** `POST /machines/{sid}/op-set_storage_layout` (maasapi.md:5921) defines whole-machine layouts (flat, lvm, bcache, etc.). v0.4.0 exposes the primitives; layout composition is a v0.5.0 concern.
- **Filesystems beyond block-device/partition mount/unmount.** No new filesystem operations.
- **Tags on RAID/VG/LV.** Existing `tag_machine` / `untag_machine` work at the machine level; per-resource tag endpoints exist but are out of scope.
- **Network block devices (iSCSI, etc.).** Different MAAS surface entirely; not storage-tier adjacent.
- **Any structural refactor of `_common.py` registration.** v0.4.0 follows the established pattern: each verb class has its own file with a `register(mcp)` method.

### `create_raid` signature and body

```python
async def run(
    self,
    client: Annotated[MaasClient, SkipJsonSchema()],
    system_id: str,
    level: int,
    name: str | None = None,
    uuid: str | None = None,
    block_devices: list[int] = [],
    partitions: list[int] = [],
    spare_devices: list[int] = [],
    spare_partitions: list[int] = [],
    confirm: bool = False,
) -> dict[str, Any]:
    _validate_ids(system_id)
    if level not in (0, 1, 5, 6, 10):
        raise ValueError(f"raid level must be 0, 1, 5, 6, or 10 (got {level})")
    if not (block_devices or partitions):
        raise ValueError("raid requires at least one block device or partition")
    if confirm is not True:
        raise ValueError(
            "create_raid is destructive; pass confirm=True to proceed. "
            f"Affected: system_id={system_id}, level={level}"
        )
    body: dict[str, Any] = {"level": level}
    if name is not None:           body["name"] = name
    if uuid is not None:           body["uuid"] = uuid
    if block_devices:              body["block_devices"] = block_devices
    if partitions:                 body["partitions"] = partitions
    if spare_devices:              body["spare_devices"] = spare_devices
    if spare_partitions:           body["spare_partitions"] = spare_partitions
    resp = await client.post(raids_path(system_id), json=body)
    if not isinstance(resp, dict):
        raise ValueError(
            f"MAAS returned non-dict for created raid (got {type(resp).__name__}); schema drift?"
        )
    return resp
```

`update_raid` mirrors this with `add_*` / `remove_*` fields (maasapi.md:8844–8858). No `level` on update.

### `create_volume_group` signature

```python
async def run(
    self,
    client: Annotated[MaasClient, SkipJsonSchema()],
    system_id: str,
    name: str,
    uuid: str | None = None,
    block_devices: list[int] = [],
    partitions: list[int] = [],

```

`update_volume_group` mirrors this with `add_*` / `remove_*` fields (maasapi.md:12282–12288).

### `create_logical_volume` and `delete_logical_volume`

Both take `vg_id` in the path, `lv_id` only on delete (body field, maasapi.md:12376). Both confirm-gated. These are write-only; the verb descriptions tell the agent to verify via `get_volume_group`.

### `storage_summary` evolution

```python
async def run(self, client, system_id) -> dict[str, Any]:
    _validate_ids(system_id)

    # Stage 1: block devices (sequential — sizes Stage 2 partition fan-out)
    devices_resp = await client.get(block_devices_path(system_id))
    devices = _parse_block_devices(devices_resp)

    # Stage 2: per-device partitions + raids + volume groups in parallel
    partition_lists, raids_resp, vgs_resp = await asyncio.gather(
        *(client.get(partitions_path(system_id, d["id"])) for d in devices),
        client.get(raids_path(system_id)),
        client.get(volume_groups_path(system_id)),
        return_exceptions=True,
    )

    partitions = _sum_partitions(partition_lists)
    raids = _parse_raids(raids_resp)
    vgs = _parse_volume_groups(vgs_resp)
    logical_volumes = sum(_count_lvs_in_vg(vg) for vg in vgs)
    total_gib = sum(_to_gib(d.get("size", 0)) for d in devices)

    return {
        "system_id": system_id,
        "block_devices": len(devices),
        "partitions": partitions,
        "total_size_gb": total_gib,
        "raid_devices": len(raids),
        "volume_groups": len(vgs),
        "logical_volumes": logical_volumes,
    }
```

`_parse_raids` accepts the wrapped shape `{"raids": [...]}` and the bare-list shape, like the existing partition parser. Same for `_parse_volume_groups`. `_count_lvs_in_vg` tries `vg["logical_volumes"]`, `vg["volumes"]`, then `0`. This mirrors the existing v0.3.0 `storage_summary` shape-tolerance pattern.

## Data Flow

Unchanged from v0.3.0/v0.3.1. All new verbs follow: FastMCP receives tool call → `run(...)` validates ids via `_validate_ids` → body-field checks → confirm gate (destructive only) → `client.get/post/put/delete` → optional M2 schema-drift raise → return value. `storage_summary` is the only verb with multi-call flow; its option-B shape keeps the existing two-stage discipline.

## Risks

- **MAAS response shape for VG `logical_volumes` field is undocumented.** Best-effort extraction with `0` fallback; an agent relying on the LV count will see `0` if MAAS uses an unexpected key name. Mitigation: documented in spec and in the `_count_lvs_in_vg` docstring. If real MAAS data reveals a different field name, v0.4.1 fixes it surgically.
- **`create_raid` `level` validation is opinionated.** Standard mdadm levels are 0/1/5/6/10, but MAAS may accept other levels. We restrict to the standard set; if MAAS adds new levels, the validation list updates. Agents passing an exotic level see a clear local error instead of a MAAS 4xx.
- **Stage 2 gather size grows with the third resource.** From N (partitions only) to N+2. `asyncio.gather` handles this transparently, but the latency floor becomes `max(N × T_single, T_raids, T_vgs)`. For typical machines with 2-4 devices and sub-second MAAS latency, total time stays well under 2s.
