# v0.5.0 — Networking: Interfaces, Bonds, VLANs, Subnets, Fabrics, Spaces, IP Ranges

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Close the networking gap surfaced in v0.4.0 user Q&A — bring curated-verb coverage to Fabric / Space / VLAN / Subnet / IP Range / Interface, expose bond creation and VLAN assignment on interfaces, and ship one composite `network_layout(system_id)` read that returns the full interface → VLAN → subnet → fabric tree in a single round-trip. Curated surface goes from 43 verbs to 78.

**Architecture:** Add 35 new curated verbs plus 14 path helpers in a new `_network_paths.py` module (sibling to `_storage_paths.py`). Use the same `class FooTool` + `Annotated[MaasClient, SkipJsonSchema()]` + `_validate_ids` + `confirm` gate + M2-raise-on-non-dict pattern that v0.3.0 / v0.3.1 / v0.4.0 established. New composite verb `network_layout` follows the same sequential-Stage-1 / data-driven-Stage-2 fetch discipline as `storage_summary`.

**Tech Stack:** Python 3.12+, FastMCP, Pydantic v2, respx (test mocking), pytest-asyncio, ruff, mypy --strict. Same stack as v0.3.0 / v0.3.1 / v0.4.0; no new dependencies.

## Background

v0.4.0 (`b051680`) shipped RAID + VG + LV on top of v0.3.0's block devices + partitions, bringing the curated surface to 43 verbs (all machine/storage/tag related). During the v0.4.0 final review the user asked: *"can it also create a bond and assign a vlan then give a subnet to that vlan?"* — verification confirmed the curated layer has zero networking verbs, and the generated layer (7 tools: machines_allocate/list/read/release + tags_list) also has zero. MAAS supports all of it (`maasapi.md` has Fabric/Fabrics at :3126/:3216, VLAN/VLANs at :11338/:11450, Subnet/Subnets at :10635/:10865, IP Range/IP Ranges at :3521/:3623, Interface/Interfaces at :3672/:4041, Space/Spaces at :10371/:10459), but the MCP exposes none of it.

Networking writes mutate cluster-wide topology (a typo'd VLAN ID can affect every machine on a fabric) where storage writes were per-machine. The v0.4.0 confirm-gate-only safety model is preserved per user decision; no pre-flight business-rule checks.

## Global Constraints

These apply to every change in v0.5.0 unless explicitly overridden. Re-read before each task's review.

- **No new dependencies.** Same `pyproject.toml` as v0.4.0.
- **`_validate_ids` is the only validator.** Every new verb validates its path IDs through `_validate_ids(system_id, ...)` — never inline `if not system_id` / `if id <= 0` blocks. The function currently lives in `_storage_paths.py`; it is generic over ID names, so networking verbs import from `_storage_paths` rather than `_network_paths`. No duplication.
- **`confirm: bool = False` on every destructive verb.** Path validation runs BEFORE the confirm check, preserving the v0.3.1 M6 invariant. Destructive networking verbs are:
  - Fabric: `create_fabric`, `update_fabric`, `delete_fabric`
  - Space: `create_space`, `update_space`, `delete_space`
  - VLAN: `create_vlan`, `update_vlan`, `delete_vlan`
  - Subnet: `create_subnet`, `update_subnet`, `delete_subnet`
  - IP Range: `create_ip_range`, `update_ip_range`, `delete_ip_range`
  - Interface: `create_interface`, `delete_interface`, `assign_vlan_to_interface`, `create_bond`, `create_bridge`, `create_interface_vlan`, `unlink_subnet`
- **`Annotated[MaasClient, SkipJsonSchema()]` first-param pattern** on every verb's `run` signature.
- **MCPUpstreamError body-strip security fix (`5ad4a1a`) preserved.** Tests asserting on upstream errors continue to assert on the status code only, never on body text.
- **Schema-drift raise on non-dict upstream (M2).** Every `get_*` and `create_*` verb raises `ValueError("MAAS returned non-dict for ...; schema drift?")` instead of silently returning `{}` or the raw body. This extends the v0.3.1 / v0.4.0 M2 fix to networking.
- **`MaasClient.post()` signature is `async def post(self, path, *, json=None) -> Any`.** Same kwarg name `json=` as v0.4.0.
- **MAAS authority.** Every endpoint shape, body field name, and response contract comes from `maasapi.md` at the project root.
- **No `Annotated[..., SkipJsonSchema()]` for body fields.** Only the `client` parameter needs the annotation.
- **Local-only, no PyPI publish, no push.** Matches v0.3.0 / v0.3.1 / v0.4.0 precedent.
- **Flat layout under `src/maasmcp/curated/`.** Networking verbs go directly into the existing flat directory (no subpackage). Matches v0.3.0/v0.4.0 shape; the day it hurts we'll know.
- **`v0.5.0` tag at post-review HEAD.** No push.

## Decisions

1. **35 new verbs, six resource families + one composite read.** Fabrics (5), Spaces (5), VLANs (5), Subnets (5), IP Ranges (5), Interfaces (9), `network_layout` (1). Total curated surface: 43 + 35 = 78.

2. **`_network_paths.py` is the path-helper module.** 14 functions covering the 6 URL spaces (`/fabrics/`, `/spaces/`, `/vlans/`, `/subnets/`, `/ipranges/`, `/nodes/{system_id}/interfaces/` with nested ops). Same one-line f-string shape as `_storage_paths.py`. The `MaasClient.post()` and other client methods take a path string; the helper is the single source of truth.

3. **`create_vlan` (cluster-level) and `create_interface_vlan` (nested on interface) are two different verbs.** MAAS exposes two `create_vlan` endpoints — `POST /vlans/` (fabric-scoped VLAN) and `POST /nodes/{sid}/interfaces/{id}/op-create_vlan` (interface-scoped child VLAN). Both surface as MCP verbs, disambiguated by name. Same for `create_bond` (nested only — no cluster-level equivalent).

4. **`network_layout` is read-only.** No confirm gate. Returns a single dict with the assembled tree per the shape in Section 8.

5. **`network_layout` fan-out is data-driven.** Stage 1 fetches `list_interfaces(system_id)` + the small cluster-wide lists (`list_fabrics`, `list_spaces`, `list_subnets`). Stage 2 fans out per-fabric VLAN fetches **after** Stage 1 reveals which fabrics the machine touches. Final assembly is in-memory join. This is the same Stage-1-must-come-first discipline as `storage_summary`, but Stage 2 is data-driven because VLANs are fabric-scoped.

6. **Subnet parameters.** `create_subnet` accepts `cidr` (required), `fabric_id` (optional, MAAS can infer from `vlan` if given), `vlan` (optional), `gateway_ip` (optional), `name` (optional), plus `confirm`. `update_subnet` accepts any of the optional fields plus `confirm`.

7. **VLAN parameters.** `create_vlan` requires `vid` (1–4094) and `fabric_id`. Optional `name`, `description`. `update_vlan` accepts optional `name`/`description` and is cluster-wide destructive on `vid` if changed (MAAS enforces — we just pass it through). `vid` validation is `if not 1 <= vid <= 4094: raise ValueError` (matches MAAS behavior).

8. **Interface write verbs follow MAAS nested-op shapes verbatim.** `create_bond(system_id, parent_id, name, bond_mode, members, vlan=None, confirm=False)` POSTs `op-create_bond` on the parent interface. `create_bridge` is the same shape with bridge instead of bond. `create_interface_vlan(system_id, parent_id, vlan, confirm=False)` POSTs `op-create_vlan`. `unlink_subnet(system_id, iface_id, subnet_id, confirm=False)` POSTs `op-unlink_subnet`. (MAAS also exposes `op-link_subnet` and `op-mark-interface-as-connected`; both are deferred to v0.6.0 since the workflow you described works without them — `link_subnet` requires a `mode` parameter set we don't need to commit to yet.)

9. **No pre-flight business-rule checks beyond what MAAS itself enforces.** Per user decision: confirm gate is the only friction. Cluster-wide destructive writes (`delete_fabric`, `delete_vlan`, etc.) propagate MAAS errors as-is — the agent (or the human reading the confirm prompt) is responsible for noticing impact.

10. **No retry/timeout changes.** Same `_request` infrastructure as v0.4.0. `network_layout` may be the slowest verb at MAAS scale (4 cluster-wide + per-fabric + per-machine interface list); that's documented in the verb description.

11. **Naming for nested interface ops is suffixed where ambiguous.** `create_vlan` (cluster) vs `create_interface_vlan` (nested) keeps the names unambiguous. `create_bond` (only nested — no cluster-level) stands alone. `unlink_subnet` (nested-only, `link_subnet` deferred to v0.6.0) stands alone.

## Scope: Out of v0.5.0

- **DHCP relay/snippets on subnets.** MAAS exposes subnet-level DHCP config (relay, snippets). v0.5.0 covers subnet CRUD only; DHCP config is a v0.6.0 concern.
- **IP range reservation by machine.** `create_ip_range` covers static reservations at the subnet level; the MAAS endpoint that pins a range to a specific machine is not exposed.
- **Storage layouts.** `POST /machines/{sid}/op-set_storage_layout` is still out of scope (deferred from v0.4.0).
- **Live console / serial access.** v0.4.0 Q&A flagged this as out-of-band for MCP.
- **Tag operations on network resources.** `tag_machine` / `untag_machine` cover the machine-level surface; per-network-resource tag endpoints are deferred.

## Section 8: Data Flow — `network_layout(system_id)`

```
Inputs: system_id (str)

Stage 1 (parallel, asyncio.gather(return_exceptions=True)):
  - GET /nodes/{system_id}/interfaces/       # determines which fabrics matter
  - GET /fabrics/                            # small, ~few items
  - GET /spaces/                             # small
  - GET /subnets/                            # cluster-wide; we filter to relevant later

Stage 2 (parallel, asyncio.gather, data-driven by Stage 1):
  - For each unique fabric_id found in interfaces[].fabric (or via vlan→fabric):
      GET /fabrics/{id}/vlans/              # VLANs are fabric-scoped
  - (IP ranges are subnet-scoped; fetched on-demand per subnet if a subnet's
     vlan_id matches a machine interface. Implementer decides per-verb
     whether to include ip_ranges inline or require a follow-up
     list_ip_ranges(subnet_id=...) call.)

Stage 3 (in-memory join):
  Build tree: machine → interfaces[] → {vlan, fabric} → {subnets[], ip_ranges[]}

Return shape (single dict):
{
  "system_id": str,
  "fabric_count": int,
  "vlan_count": int,
  "subnet_count": int,
  "interface_count": int,
  "ip_range_count": int,
  "interfaces": [
    {
      "id": int,
      "name": str,
      "type": str,                       # physical | bond | bridge | vlan | unknown
      "mac_address": str | None,
      "vlan": {"id": int, "name": str | None, "vid": int, "fabric_id": int} | None,
      "linked_subnet": {"id": int, "cidr": str, "gateway_ip": str | None} | None,
      "parents": [int],                  # for bonds/bridges
      "ip_addresses": [str],
      "children": [int],                 # for bonds/bridges (mirror of parents)
    }
  ]
}

Notes on the shape:
  - Subnets are deduplicated across interfaces (one subnet may serve many).
  - ip_range_count is the union of all IP ranges on the linked subnets.
  - "type" is derived from MAAS's interface.type field; "unknown" is the
    fallback for unrecognized MAAS types.
  - "fabric_count" is the number of distinct fabrics the machine touches.
```

## Risks / non-obvious calls

1. **Nested-op naming.** The cluster-level `create_vlan` and the
   interface-nested `create_vlan` (renamed `create_interface_vlan`) need
   careful docstring separation so the agent can pick the right one. The
   plan's per-verb task includes a "name confusion test" — a unit test that
   asserts `create_vlan.path != create_interface_vlan.path`.

2. **`network_layout` Stage 2 depends on Stage 1.** If `list_interfaces`
   fails, the VLAN fan-out can't proceed; we fall back to "we know the
   cluster-wide VLAN count, but per-machine topology is partial." The verb
   returns `partial=True` plus an `errors` list in that case.

3. **`create_bond` `bond_mode` validation.** MAAS supports multiple bond
   modes (balance-rr, active-backup, balance-xor, broadcast, 802.3ad,
   balance-tlb, balance-alb). The verb accepts `bond_mode: str` and passes
   it through; MAAS enforces the allowed set. We do NOT add a custom
   allow-list — `maasapi.md` doesn't document one and MAAS will 4xx on
   invalid input.

4. **Empty subnet CIDR.** `create_subnet` requires `cidr` to be a valid
   CIDR string. Use `ipaddress.ip_network(cidr)` to validate; raise
   `ValueError` on parse failure.

5. **Reuse of `_validate_ids` from `_storage_paths`.** The function is
   generic (`**ids: int`), but its home module is named `_storage_paths`.
   Two options: rename the module to `_id_validators.py`, OR import the
   function from `_storage_paths` in `_network_paths`. Plan recommends the
   second (zero churn, no module rename, validates the M1 finding
   protection). Document the cross-domain import in a docstring.
