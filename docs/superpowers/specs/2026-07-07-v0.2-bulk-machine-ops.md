# v0.2.0 — Bulk Machine Operations + List Filters

## Goal

Extend the maasmcp curated layer so an agent can run fleet-wide machine operations without N round-trips, and filter `list_machines` by hardware traits so an agent can scope queries server-side.

## New surface

**Four bulk verbs (additive, MCP-tool form follows the existing Tool class shape):**

- `bulk_release_machines(system_ids, comment=None, erase=True, secure_erase=False, quick_erase=False, force=False)` — uses MAAS's batch endpoint `POST /api/2.0/machines/op-release` with a `machines=<list-of-system_ids>` body field. Single MAAS round-trip. Per-system_id status in the response (never raises on partial failure).
- `bulk_tag_machines(system_ids, tag)` — fans out over per-id `POST /api/2.0/tags/{tag}/op-update_nodes` with `add=<system_id>`. MAAS has no batch tag endpoint.
- `bulk_untag_machines(system_ids, tag)` — fans out over per-id `POST /api/2.0/tags/{tag}/op-update_nodes` with `remove=<system_id>`.
- `bulk_power_control_machines(system_ids, action)` — fans out over per-id `POST /api/2.0/machines/{system_id}/op-power_{on|off|cycle}`. MAAS has no batch power endpoint.

**Three new optional kwargs on `list_machines`:**

- `zone` — server-side filter via MAAS's `zone` query param.
- `cpu_count_min` — server-side filter mapped to MAAS's `cpu_count` query param (MAAS docs: "minimum number of CPUs").
- `memory_min` — server-side filter mapped to MAAS's `mem` query param (MAAS docs: "minimum amount of RAM in MiB").

All three new kwargs are optional. Existing callers pass nothing and get identical behaviour.

## Decisions

1. **Return shape (uniform across all four bulk verbs):** every bulk verb returns `list[dict[str, Any]]` of `{system_id, status: "ok"|"error", result? | error?}`. Order matches input order. Verb never raises on partial failure — the agent decides what to retry.
2. **Fan-out cap:** `asyncio.Semaphore(10)` on every per-id POST in `bulk_tag_machines`, `bulk_untag_machines`, `bulk_power_control_machines`. Module-level constant `_FANOUT_CONCURRENCY = 10`.
3. **`bulk_release_machines` uses one MAAS call** (the `/api/2.0/machines/op-release` endpoint accepts a `machines` list). The other three bulk verbs fan out via `asyncio.gather(..., return_exceptions=True)` because MAAS exposes only per-id endpoints for them. This is documented in `maasapi.md`.
4. **Naming convention for bulk verbs:** prefix `bulk_` and reuse the singular verb name (`bulk_release_machines`, not `release_machines_bulk`). Matches the existing `find_available_machines`/`get_machine` style.
5. **`list_machines` kwargs use `_min` suffix** (`cpu_count_min`, `memory_min`) even though MAAS's own param is `cpu_count`/`mem`. The `_min` makes the minimum semantics explicit to the agent; internally we map to MAAS's quirky param names.
6. **Version bump 0.1.1 → 0.2.0.** Surface is additive but the new verbs can hammer MAAS; a minor bump signals "test before depending."

## Constraints

- **MAAS authority:** every endpoint shape, body field name, and response contract comes from `maasapi.md` at the project root. Verified against `maasapi.md` lines 6141–6153 (list-machines query params), 6543–6580 (bulk release), 11142–11170 (tag update_nodes), 5604–5700 (per-id power ops).
- **No new dependencies.** All imports already exist (`asyncio`, `typing`, `pydantic`, `respx`, `pytest-asyncio`).
- **Tool registration:** each new tool goes in `src/maasmcp/curated/<name>.py` with the same `class XxxTool: name / description / async run / def register(mcp)` shape as the existing 12, registered in `src/maasmcp/curated/_common.py`.
- **Coverage gate:** curated-layer coverage ≥85%; new tools and modified `list_machines` ≥90%.
- **Lint/type gate:** `ruff check src tests` and `mypy --strict src` must pass clean before each commit.
- **Push/tag policy:** local tag only; push only after explicit user consent. Never push to main/master without consent.

## Out of scope

- KVM/virtualisation verbs (mentioned in brainstorming as a future direction).
- Subnet/DHCP/DNS verbs.
- Per-tool retry policies beyond the existing MAAS client retry (5xx + network-timeout, 3 attempts).
- Cursor-based pagination for huge machine lists (the existing auto-pagination is per-tool; this is unchanged).

## Risks

- **Fan-out at scale:** a 1000-host bulk release produces 1000 per-id POSTs for tag/power, capped at 10 concurrent. Wall-clock for 1000 hosts at 100ms RTT ≈ 10s. Acceptable for an agent's request lifecycle. No backpressure mechanism — an agent that calls this with 10k hosts will block for ~100s.
- **`bulk_release_machines` MAAS response shape:** the docs say "A JSON object containing a list of release machines" but the in-the-wild response may include a top-level object with a `machines` field rather than a flat list. The implementation handles both (`response if isinstance(response, list) else []`) but the unit test only covers the flat-list case. E2E test will surface the actual shape.
- **Test isolation:** all bulk verbs use `asyncio.gather` with a fresh `Semaphore` per call, so no shared state between calls. No test isolation risk beyond the standard asyncio-mode issues already handled.
