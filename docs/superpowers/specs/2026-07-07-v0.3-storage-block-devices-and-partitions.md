# v0.3.0 — Storage Verbs (Block Devices + Partitions)

## Goal

Give an agent a safe, complete, agent-friendly way to inspect and modify block-device and partition layout on a MAAS machine, behind a `confirm: bool` safety gate. This is the first release in the storage series; RAID and volume groups land in v0.4.0.

## New surface

**5 read verbs (no gate):**

- `list_block_devices(system_id)` — GET `/api/2.0/nodes/{system_id}/blockdevices/`. Returns MAAS's response (list of dicts).
- `get_block_device(system_id, block_device_id)` — GET path-templated. Returns MAAS's response (dict).
- `list_partitions(system_id, block_device_id)` — GET `/api/2.0/nodes/{system_id}/blockdevices/{device_id}/partitions/`. Returns list of dicts.
- `get_partition(system_id, block_device_id, partition_id)` — GET path-templated. Returns dict.
- `storage_summary(system_id)` — cross-resource read. Two-stage fetch: first `list_block_devices` (sequential), then `asyncio.gather` of N× `list_partitions` where N is the block device count. Returns a flattened dict with block-device count, partition count, total size in GB, plus `raid_devices=0` and `volume_groups=0` placeholders (RAID/VG counts land in v0.4.0 when those endpoints are curated; the placeholders keep the response shape stable across releases).

**10 destructive verbs (gated on `confirm: bool = False`).** Parameter lists below use `...` to mean "additional optional kwargs from the MAAS PUT/POST body schema; the implementation plan enumerates them verbatim from `maasapi.md`."

- `create_block_device(system_id, name, size, block_size, model?, serial?, id_path?, confirm=False)` — POST.
- `update_block_device(system_id, block_device_id, name?, model?, serial?, ..., confirm=False)` — PUT.
- `delete_block_device(system_id, block_device_id, confirm=False)` — DELETE.
- `set_boot_disk(system_id, block_device_id, confirm=False)` — POST `op-set_boot_disk`.
- `format_block_device(system_id, block_device_id, fstype, uuid?, confirm=False)` — POST `op-format`.
- `create_partition(system_id, block_device_id, size, fstype?, ..., confirm=False)` — POST.
- `delete_partition(system_id, block_device_id, partition_id, confirm=False)` — DELETE.
- `format_partition(system_id, block_device_id, partition_id, fstype, ..., confirm=False)` — POST `op-format`.
- `mount_partition(system_id, block_device_id, partition_id, mount_point, mount_options?, confirm=False)` — POST `op-mount`.
- `unmount_partition(system_id, block_device_id, partition_id, confirm=False)` — POST `op-unmount`.

**1 shared helper module:**

- `_storage_paths.py` — path-templating helpers for `/nodes/{system_id}/blockdevices/...` paths. Single source of truth to prevent drift across the 10 verbs that touch this URL space.

## Decisions

1. **Safety gate is uniform across all destructive verbs.** Every destructive verb takes `confirm: bool = False`. If `confirm=False`, raise `ValueError` before any MAAS call. The error message names the operation and the affected resource so the agent can verify it's targeting the right thing before retrying with `confirm=True`. Mount/unmount use the same gate — unmounting a wrong filesystem has user-visible impact, so it's "destructive" for this purpose.
2. **4 distinct return shapes, contract by verb category:**
   - Reads (`list_*`, `get_*`) — return MAAS's response as-is (`list[dict]` or `dict`).
   - Creates (`create_*`) — return MAAS's POST 200 response (the newly-created resource as `dict`).
   - Status-changes (update, set_boot_disk, format_*, mount_*, unmount_*) — return `{"status": "ok", "system_id", "resource_id", "operation"}`.
   - Deletes — return `{"status": "ok", "system_id", "resource_id", "operation": "delete"}`.
3. **Path validation up front:** `system_id` non-empty (matches existing `get_machine`), `block_device_id` / `partition_id` must be `> 0`, `mount_point` must start with `/`. Validate before the safety gate so empty-id + confirm=True still fails fast (no MAAS round-trip).
4. **`storage_summary` fans out via `asyncio.gather`** (matches existing `summary.py` pattern from commit `ce5ee02`). Two-stage fetch: first `list_block_devices` (sequential, returns the device list), then `asyncio.gather` of N× `list_partitions` where N is the block device count. Block-device-list 404 (machine not found) propagates as `MCPUpstreamError`.
5. **No bulk semantics.** Storage operations are per-machine (typical machine has 1–10 block devices). The bulk-fan-out pattern from v0.2.0 doesn't apply here — there is no MAAS multi-device endpoint for partition/format/mount, and a single agent request targets one machine at a time.
6. **One verb per file, ~40 lines each.** 15 new files under `src/maasmcp/curated/`. Matches the v0.2.0 file-per-verb convention. The mental load of a 15-file PR is lower than the mental load of a 600-line `storage.py` with 14 classes.
7. **Version bump 0.2.0 → 0.3.0.** Surface adds destructive verbs — minor bump signals "test before depending." Same convention as the v0.1.1 → v0.2.0 bump.

## Constraints

- **MAAS authority:** every endpoint shape, body field name, and response contract comes from `maasapi.md` at the project root. Verified against `maasapi.md` lines 584–620 (block device), 1060–1120 (block devices collection), 7965–8230 (partitions + partition ops), 8750–8900 (RAID — referenced, not implemented), 12190–12300 (volume group — referenced, not implemented).
- **No new dependencies.** All imports already exist (`asyncio`, `typing`, `pydantic`, `respx`, `pytest-asyncio`).
- **Tool registration:** each new tool goes in `src/maasmcp/curated/<name>.py` with the same `class XxxTool: name / description / async run / def register(mcp)` shape as the existing 16 verbs. Registered in `src/maasmcp/curated/_common.py` in the order: reads first, then block-device writes, then partition writes. (Single registration block; the plan will pin the exact order to prevent drift.)
- **Path templating:** all path construction goes through `src/maasmcp/curated/_storage_paths.py`. No inline `f"/nodes/{system_id}/..."` anywhere else. The plan will mandate this.
- **`confirm` gate placement:** validate path params first, then check `confirm`, then issue the MAAS call. Empty `system_id` + `confirm=True` must still raise `ValueError` before any HTTP call.
- **`MCPUpstreamError` body-strip semantics (security fix `5ad4a1a`):** tests assert on status code only (`"409" in str(err)`), never on MAAS response body text. This was a v0.2.0 final-review finding (I1); the plan's per-task review must verify each test follows this rule.
- **Coverage gate:** curated-layer coverage ≥85%; new storage tools and modified `_common.py` ≥90% line coverage; 100% branch coverage on the `confirm` gate (both `confirm=True` and `confirm=False` paths hit by tests).
- **Lint/type gate:** `ruff check src tests` and `mypy --strict src` must pass clean before each commit.
- **Plan pre-flight (process improvement):** the v0.2.0 plan needed 5 mid-flight corrections because it didn't pre-verify v0.1.1's external dependencies. The v0.3.0 plan must explicitly pre-verify these against current `main` before dispatching:
  - `MaasClient.post`/`get`/`delete` signatures and how `json=` is converted to multipart.
  - The `tests/conftest.py` env-clear fixture and the minimum required `MAASMCP_*` env vars to override it.
  - The `async with maas_client:` block requirement (respx context must be outer).
  - `MCPUpstreamError.__str__` returns `"upstream <status>"` only (body stripped).
  - The `_fanout.py` module pattern for shared constants (the analogous pattern for `_storage_paths.py`).
  This pre-flight list is a global constraint, not just an authoring preference — it's the single highest-leverage improvement from the v0.2.0 retrospective.
- **Push/tag policy:** local tag only; push only after explicit user consent. Never push to main/master without consent.

## Out of scope

- RAID (`/nodes/{system_id}/raid/...`) — 5 endpoints, deferred to v0.4.0.
- Volume groups (`/nodes/{system_id}/volume-group/...`) — 5 endpoints, deferred to v0.4.0.
- Subnet/DHCP/DNS verbs (mentioned in brainstorming as a future direction).
- KVM/virtualisation verbs (mentioned in brainstorming as a future direction).
- Per-tool retry policies beyond the existing MAAS client retry (5xx + network-timeout, 3 attempts).
- Slim-view variants of `list_block_devices` / `list_partitions` (the existing verb returns MAAS's full shape; a slim view is a follow-on if agent feedback demands it).
- Network/subnet/observability sub-surfaces.

## Risks

- **Destructive verbs without agent confirmation flow.** The `confirm: bool = False` gate is the only thing standing between an LLM agent and `delete_block_device` on a production disk. The plan MUST include explicit tests asserting `not mock.calls.call_count == 0` when `confirm=False`. If those tests are missing or weak, the gate is theatre.
- **Mount/unmount semantics.** Unmounting a filesystem on a running machine can break running services. The `confirm` gate covers this, but agents may pass `confirm=True` reflexively. The plan will require `mount_partition`'s description to warn explicitly: "Unmounting a mounted filesystem can disrupt running services. Verify the target is correct before passing `confirm=True`."
- **`storage_summary` parallelism.** A machine with many block devices + partitions produces 5 parallel GETs. If MAAS is slow under concurrent reads, this could hit the client's 5xx-retry loop and take 5–10s. Acceptable; the existing `summary` tool already does parallel reads.
- **MAAS response shape drift on creates.** `maasapi.md` says creates return "A JSON object containing a list of block devices" — the actual response on POST is the created resource as a dict, not a list. The implementation assumes the dict shape; the e2e test will catch any drift.
- **Test isolation.** All storage verbs use `client.get`/`post`/`put`/`delete` directly with a fresh `MaasClient` per test (matches existing test pattern). No shared state between tests beyond the env-var fixture.
