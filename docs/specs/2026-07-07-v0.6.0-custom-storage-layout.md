# v0.6.0 — Custom Storage Layout Composite

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Close the storage-layout gap surfaced in v0.5.0 user Q&A — provide one curated verb `apply_storage_layout(system_id, layout, confirm=False)` that builds a multi-disk layout (e.g. RAID 1 with `/boot/efi` off-array, RAID 0/5/6/10, plain partition tables) by sequencing the existing leaf CRUD verbs. Plus a README recipe section so agents can drive the leaf verbs directly when they need finer control. One new verb brings the curated surface from 78 to 79.

**Architecture:** One new curated verb `apply_storage_layout.py` that takes a typed Python-dict spec, validates it pre-flight, then sequentially calls `create_partition` → `format_partition` → `mount_partition` → `create_raid` → `set_boot_disk` (and similar for the supported shapes). Verifies each step via a follow-up `get_*` call before continuing. On any mid-sequence failure, returns `status="partial"` with `completed_steps`, `failed_step`, `errors`, and a rollback hint pointing at `op-restore_storage_configuration` (out of curated surface — agent decides). The verb is the only new code; it is a pure orchestrator over the existing v0.3.0/v0.4.0 leaf surface.

**Tech Stack:** Python 3.12+, FastMCP, Pydantic v2, respx (test mocking), pytest-asyncio, ruff, mypy --strict. Same stack as v0.3.0 / v0.3.1 / v0.4.0 / v0.5.0; no new dependencies.

## Background

v0.5.0 (`9bf7460`) shipped 35 networking verbs + `network_layout` composite, bringing the curated surface to 78 verbs. During v0.5.0 user Q&A the user asked: *"i've set maas to no storage blank layout configuration option which leaves it blank so we can configure it how we need"* and described the target flow: *"commission node → build RAID 1 from two disks with `/boot/efi` carved out on raw disks → bond the two NICs → VLAN 100 on the bond → subnet on VLAN 100 → deploy Ubuntu 24.04."* All of this is exposed at the leaf level already (create_partition, format_partition, mount_partition, create_raid, set_boot_disk), but the agent has to know the correct call order, the partition-of-purpose mapping, and the boot-disk requirement. That's a knowledge burden the user shouldn't have to encode in every prompt.

`op-set_storage_layout` (`docs/reference/maasapi.md:5921`) cannot express this layout — it only accepts preset names (`flat`, `lvm`, `bcache`, `vmfs6`, `vmfs7`, `custom`, `blank`), and the `custom` value points at a commissioning script that lives outside the MCP surface. Custom layouts in MAAS are built by composing leaf CRUD calls; the `apply_storage_layout` composite encodes that composition in one verified verb.

## Global Constraints

These apply to every change in v0.6.0 unless explicitly overridden. Re-read before each task's review.

- **No new dependencies.** Same `pyproject.toml` as v0.5.0.
- **`_validate_ids` is the only validator.** Every new verb validates its path IDs through `_validate_ids(system_id, ...)` — never inline `if not system_id` / `if id <= 0` blocks. The function lives in `_storage_paths.py` and is reused.
- **`confirm: bool = False` on every destructive verb.** `apply_storage_layout` is destructive (mutates a machine's storage layout); it carries the standard `confirm` gate. Spec validation runs BEFORE the confirm check, preserving the v0.3.1 M6 invariant.
- **`Annotated[MaasClient, SkipJsonSchema()]` first-param pattern** on every verb's `run` signature.
- **MCPUpstreamError body-strip security fix (`5ad4a1a`) preserved.** Tests asserting on upstream errors continue to assert on the status code only, never on body text.
- **Schema-drift raise on non-dict upstream (M2).** Every step's `get_*` verification raises `ValueError("MAAS returned non-dict for ...; schema drift?")` instead of silently returning `{}` or the raw body.
- **`MaasClient.post()` / `.put()` signatures unchanged.** `async def post(self, path, *, json=None) -> Any`. Same kwarg name `json=` as v0.5.0.
- **MAAS authority.** The leaf verbs we call are already wired against the MAAS endpoints documented in `docs/reference/maasapi.md`. The composite does NOT introduce new MAAS endpoints; it only sequences existing leaf calls.
- **No `Annotated[..., SkipJsonSchema()]` for body fields.** Only the `client` parameter needs the annotation.
- **Local-only, no PyPI publish, no push.** Matches v0.3.0 / v0.3.1 / v0.4.0 / v0.5.0 precedent.
- **Flat layout under `src/maasmcp/curated/`.** `apply_storage_layout.py` goes directly into the existing flat directory (no subpackage). Matches v0.3.0 / v0.4.0 / v0.5.0 shape.
- **`v0.6.0` tag at post-review HEAD.** No push.

## Decisions

1. **One new verb.** `apply_storage_layout(system_id, layout, confirm=False)` brings the curated surface from 78 to 79. No new verbs, no new path helpers, no MAAS endpoint additions.

2. **Spec shape is block-device-id-keyed and purpose-tagged.** The agent passes a dict (not a string, not a Pydantic model — FastMCP tools accept `dict[str, Any]` for arbitrary structured input). The spec mirrors MAAS's commissioning-script vocabulary but uses MAAS `block_device_id` integers instead of `/dev/sda` paths — agents get those from `list_block_devices`. See Section 8 for the full shape.

3. **Sequential leaf execution.** Storage mutations must be sequential because later steps depend on earlier results (e.g. `format_partition` needs the `partition_id` from the prior `create_partition`). No `asyncio.gather`. This is the opposite of `network_layout`'s parallel fan-out, and it's correct here — gather would introduce race conditions on dependency-ordered writes.

4. **Verify-after-each-step.** After every leaf call, the verb calls the matching `get_*` to confirm the resource exists with the expected attributes. If verification fails (e.g. MAAS returned a dict but `get_partition` doesn't see it), the verb treats it as a mid-sequence failure and returns `partial=True`. This catches MAAS schema drift, async visibility delays, and silent failures from the upstream.

5. **No automatic rollback.** Rolling back storage mutations is risky — deleting a partition that has been written to can lose data; unformatting a filesystem that was just formatted is mostly safe but the agent may have started writing to the mount. The verb surfaces what was done (in `completed_steps`) and points at `op-restore_storage_configuration` (a raw MAAS endpoint, not exposed as a curated verb) as the recovery path. The agent decides whether to call it. This matches v0.5.0's `network_layout` partial-failure semantics (`partial=True` + `errors` list).

6. **Pre-flight validation runs before `confirm` check.** A spec missing `disks` or `boot_disk` raises `ValueError` immediately, regardless of `confirm`. This matches the v0.3.1 M6 invariant (validation before destructive gate) and lets the agent iterate on spec shape without ever needing to pass `confirm=True` for broken input.

7. **Supported shapes.** The verb handles:
   - **Plain partition table** — no RAID, one or more disks, each partitioned and optionally formatted + mounted.
   - **RAID with ESP off-array** — partitions carved on each member disk, ESP formatted `fat32` on raw disks, RAID over the remaining partitions, rootfs on RAID.
   - **RAID without ESP** — partitions carved on each member disk, RAID over all of them. No `/boot/efi` (valid only if BIOS boot, or for use cases where the bootloader sits outside MAAS).

   The spec shape carries a `layout_type` field that the verb validates against this set; unknown types raise `ValueError` before any leaf call. (LVM on top of RAID is reserved in the spec shape as `volume_group` for v0.7.0; setting it in v0.6.0 raises `NotImplementedError`. See Scope: Out of v0.6.0.)

8. **No `skip_storage` on `deploy_machine`.** MAAS cluster is configured with `default_storage_layout=blank` per user; storage configuration is the agent's responsibility via leaf calls. `skip_storage` would be a no-op given the cluster setting and is intentionally NOT added to `deploy_machine`. Documented in the README recipe.

9. **The recipe in README complements the verb.** Both are first-class. Some agents will want the explicit recipe (e.g. for educational/incremental workflows); others will want the composite. The recipe is documented as a numbered sequence of leaf calls with `confirm=True` on each destructive step.

10. **No retry / timeout changes.** Same `_request` infrastructure as v0.5.0. `apply_storage_layout` may take several seconds on real hardware (multiple MAAS round-trips per step + verify-after-each); this is documented in the verb description.

11. **Naming.** `apply_storage_layout` is unambiguous (apply a layout to a machine's storage). `build_storage_layout` and `provision_storage` were considered but read as implying more than a single transactional call. `apply_storage_layout` matches MAAS's own verb (`op-set_storage_layout`).

12. **No new path helpers.** All leaf verbs already have their path helpers in `_storage_paths.py`. The composite orchestrates calls but does not introduce new paths.

## Scope: Out of v0.6.0

- **LVM volume groups / logical volumes on top of RAID.** Spec shape has a `volume_group` field reserved in the dict but the verb raises `NotImplementedError` if it's set. v0.4.0 already has `create_volume_group` / `create_logical_volume`; sequencing them after RAID creation is straightforward but the user deferred this to v0.7.0 during scope discussion.
- **Bcache.** MAAS exposes `/nodes/{sid}/bcaches/` and `op-set_storage_layout` accepts `bcache`. The spec shape would need a `cache_device` block; deferred to v0.7.0.
- **VMFS datastores.** MAAS-specific; not relevant to general metal provisioning. Deferred indefinitely.
- **`op-restore_storage_configuration` curated verb.** The partial-failure rollback hint references this MAAS endpoint, but no curated verb wraps it. An agent can call the raw generated tool if needed. v0.7.0 if there's demand.
- **`skip_storage` parameter on `deploy_machine`.** See Decision 8; not needed given the user's MAAS cluster config.
- **`op-link_subnet` curated verb.** v0.5.0 deferred it; v0.6.0 scope explicitly does not include it (this release is storage-focused).
- **DHCP / IPAM config.** Out of v0.5.0, still out.
- **Tag operations on network / storage resources.** Still out.

## Section 8: Data Flow — `apply_storage_layout(system_id, layout, confirm)`

### 8.1 Inputs

```
system_id: str
layout: dict[str, Any]   # see 8.2
confirm: bool = False
```

### 8.2 Spec shape

```python
{
    "layout_type": "raid_with_esp" | "raid" | "plain",
    "disks": [
        {
            "block_device_id": int,         # > 0, from list_block_devices
            "partitions": [
                {
                    "size": "1G" | "512M" | "remaining",  # "remaining" maps to MAAS's "all remaining"
                    "fstype": "fat32" | "ext4" | None,   # None for raid-member partitions
                    "mount_point": "/boot/efi" | None,   # None for raid-member partitions
                },
                ...
            ]
        },
        ...
    ],
    "raid": None | {                        # present iff layout_type starts with "raid"
        "level": 0 | 1 | 5 | 6 | 10,
        "name": "md0",
        "filesystem": "ext4" | None,        # None = format later, but spec requires this set
        "mount_point": "/" | None,
    },
    "volume_group": None,                   # reserved; NotImplementedError if set
    "boot_disk": {"block_device_id": int},  # the disk MAAS will boot from
}
```

### 8.3 Example: RAID 1 with /boot/efi off-array (the user's target flow)

```python
layout = {
    "layout_type": "raid_with_esp",
    "disks": [
        {
            "block_device_id": 1,
            "partitions": [
                {"size": "1G", "fstype": "fat32", "mount_point": "/boot/efi"},
                {"size": "remaining"},  # raid member
            ]
        },
        {
            "block_device_id": 2,
            "partitions": [
                {"size": "1G", "fstype": "fat32"},  # standby mirror, no mount
                {"size": "remaining"},
            ]
        }
    ],
    "raid": {
        "level": 1,
        "name": "md0",
        "filesystem": "ext4",
        "mount_point": "/",
    },
    "boot_disk": {"block_device_id": 1},
}
```

### 8.4 Execution sequence (raid_with_esp)

```
Pre-flight (no MAAS calls):
  1. _validate_ids(system_id)
  2. Validate spec shape: layout_type in supported set, every block_device_id > 0,
     every disk has at least one partition, raid block present iff layout_type starts
     with "raid", boot_disk present, exactly one /boot/efi partition, mount_point
     "/" present (either via raid.filesystem+mount_point or via a disk partition).
     Raise ValueError on any failure.

Confirm gate (after validation, before any MAAS call):
  3. If confirm is not True: raise ValueError listing spec summary
     (system_id, layout_type, disk count, RAID level, mount points).

Sequential leaf calls (each step followed by verify-after):
  4. For each disk in disks:
       For each partition in disk.partitions:
         a. POST partitions_path(system_id, disk.block_device_id) with
            {size, fstype?, partition_table_type="gpt", bootable?}
            → expect partition dict with "id"
         b. GET partitions_path(system_id, disk.block_device_id) → verify partition exists
         c. If partition.fstype is set:
            POST format_partition_path(...) with {fstype: partition.fstype}
         d. If partition.mount_point is set:
            POST mount_partition_path(...) with {mount_point: partition.mount_point}

  5. If layout_type starts with "raid":
       POST raids_path(system_id) with {level, name, partitions=[<member_ids>]}
       → expect raid dict with "id"
       GET raids_path(system_id) → verify raid exists
       If raid.filesystem is set:
         POST format_block_device_path(system_id, raid_id) with {fstype}
         POST mount_partition_path(system_id, raid_id, raid_partition_id) with
           {mount_point: raid.mount_point}

  6. POST set_boot_disk_path(system_id, boot_disk.block_device_id) with {}
       GET block_device_path(system_id, boot_disk.block_device_id) → verify boot flag

Return:
  7a. status="complete", all created resource ids in completed_steps, no errors.
  7b. On any leaf failure or verification failure: status="partial",
      completed_steps truncated to what succeeded, failed_step with the failing
      step + error, errors list, rollback_hint string.
```

### 8.5 Return shape

```python
{
    "system_id": str,
    "layout_type": str,
    "status": "complete" | "partial",
    "completed_steps": [
        {
            "step": "create_partition",
            "disk_id": int,
            "partition_id": int,
        },
        {
            "step": "format_partition",
            "partition_id": int,
            "fstype": str,
        },
        {
            "step": "mount_partition",
            "partition_id": int,
            "mount_point": str,
        },
        {
            "step": "create_raid",
            "raid_id": int,
            "level": int,
        },
        {
            "step": "set_boot_disk",
            "block_device_id": int,
        },
        ...
    ],
    "failed_step": None | {
        "step": str,
        "params": dict[str, Any],
        "error": str,                 # repr of MCPUpstreamError or ValueError
    },
    "errors": [str, ...],
    "rollback_hint": (
        'To restore blank state, call op-restore_storage_configuration on the '
        'machine (raw MAAS endpoint, not exposed as a curated verb). Or call '
        'op-set_storage_layout with storage_layout=blank.'
    ),
}
```

### 8.6 Failure modes

1. **Pre-flight validation fails.** `ValueError` raised before `confirm` check. Examples: missing `disks`, missing `boot_disk`, missing `/` mount, `block_device_id <= 0`, unknown `layout_type`, `volume_group` set (NotImplementedError).

2. **`confirm=False`.** Standard gate. `ValueError` listing spec summary and affected `system_id`. No MAAS calls.

3. **Mid-sequence leaf failure (e.g. `create_partition` returns 409).** The `MCPUpstreamError` propagates from `MaasClient` (body-strip preserved). The verb catches it, packages it into the partial-result dict, and **returns the partial dict** — it does NOT re-raise. This matches `network_layout`'s partial-failure pattern: the caller decides whether to retry, restore, or live with the partial state. Tests assert on the partial-return shape (status="partial", failed_step populated, errors non-empty) and on the underlying MCPUpstreamError status code separately (per the v0.5.0 M2 invariant preserved from `5ad4a1a`).

4. **Verification failure.** A step succeeded at MAAS (returned a dict) but a follow-up `get_*` doesn't see the resource. Treated as a mid-sequence failure: `status="partial"`, the failed step listed, error captured. Returned as a partial dict, not raised.

5. **Asyncio error in async path.** Should not happen (no `gather`), but if it does the verb packages it as a mid-sequence failure for consistency and returns a partial dict.

No retries. Same as `deploy_machine` and v0.5.0 verbs — the agent decides whether to retry.

### 8.7 Why return-partial-not-raise

`network_layout` (v0.5.0) established the pattern of returning partial results instead of raising on mid-sequence failure. The reasoning:

- The agent has more context than the verb about whether the partial state is acceptable, restorable, or fatal. Raising forces a fixed control-flow model (try/except) onto a decision that may want explicit branching.
- The `errors` list in the partial dict is the same information an exception would carry, just structured. The agent can still fail loudly by checking `status` on return.
- It's consistent with the existing v0.5.0 surface. Two different failure modes for two different verbs would force the agent to learn two error-handling patterns.

The verb DOES still raise on:
- Pre-flight validation errors (no MAAS calls happened — no partial state to report)
- `confirm=False` (the gate, not a failure)
- `NotImplementedError` for reserved-but-unimplemented spec fields (`volume_group`)

These are all caller-error conditions, not mid-sequence failures. The agent should treat them as deterministic input-validation problems, not as "the operation partially succeeded and you need to decide what to do."

## Risks / non-obvious calls

1. **Sequencing vs. parallel fan-out.** `network_layout` uses `asyncio.gather` because its reads are independent. `apply_storage_layout` MUST be sequential because its writes have data dependencies. A future implementer might be tempted to gather; the spec and tests must enforce sequencing. The plan's test #7 (call_count + assertion that later steps don't run before earlier ones) catches this.

2. **`partition_table_type="gpt"` is implicit.** MAAS defaults to MBR for `create_partition`. For UEFI boot the ESP requires GPT, so the verb sets `partition_table_type="gpt"` automatically. This is a deliberate default — the agent doesn't specify it. If the user wants MBR (legacy BIOS), they can use the raw `create_partition` leaf verb. Documented in the verb description.

3. **`bootable` flag.** MAAS has a `bootable` flag on partitions but UEFI doesn't use it — UEFI reads the GPT type GUID. The verb does NOT set `bootable=True` on the ESP. Documented in the verb description.

4. **RAID member partition selection.** When `layout_type=raid_with_esp`, the verb selects the LAST partition on each disk (the `"remaining"` one) as a RAID member, plus any other `"remaining"` partitions. This is positional: the spec author controls membership by ordering. If a disk has more than one non-ESP partition, both go into the RAID. If a disk has only an ESP partition, it doesn't contribute to the RAID (the user explicitly declared it standalone). The verb validates that all RAID-member disks have at least one `"remaining"` partition.

5. **`op-restore_storage_configuration` is not in the curated surface.** The rollback hint references it. If a user actually needs the rollback, they'd call the raw MAAS tool or use the MAAS UI. We don't promise it works — the hint is informational. Documented as "rollback_hint" (informational), not "rollback_command" (executable).

6. **`volume_group` field is reserved but raises NotImplementedError.** Including it in the spec shape (even though unused) lets us add LVM support in v0.7.0 without breaking the spec shape. The verb's behavior is explicit: setting it raises immediately.

7. **No `skip_storage` on `deploy_machine`.** Per Decision 8 — the user's MAAS cluster is configured with `default_storage_layout=blank`, so `skip_storage` would be a no-op. If a future user has a different cluster config, they'll need a different approach (custom commissioning script, raw MAAS tool, or v0.7.0 work). Documented in the README as a known limitation.

8. **`apply_storage_layout` is destructive.** Setting `confirm=False` (default) returns `ValueError` before any MAAS call. This matches every other destructive verb in v0.5.0. The verb description explicitly notes that storage layouts are destructive and hard to recover from; the agent should preview the spec before passing `confirm=True`.
